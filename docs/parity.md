Cluster supervision, systemd support, three lock modes, concurrency claim promotion, dynamic labels, bulk/batch concurrency checks, and natural-language cron validation already exist at the release baseline. They must not be mistaken for optional future features.

DecentJob uses its own namespace, SQL schema, and PostgreSQL implementation. Direct runtime dependencies are `activejob` 8.1.4 and `pg` 1.7.0. The version numbers are the agreed target, not a claim that this document has checked the current gem registry. Active Job's transitive dependencies remain available. GoodJob's Active Record, Rails engine, concurrent-ruby, Fugit, Thor, Rack, and other direct dependencies are reference implementation choices, not permission to add runtime dependencies.

All new tests must use **Minitest spec syntax**, with `describe` and `it`. GoodJob's RSpec examples are behavioral evidence to translate. Do not copy its test framework or substitute subclass-style Minitest tests.

Parity means equivalent observable results under `DecentJob` APIs. It does not require GoodJob table compatibility, loading GoodJob, reproducing Active Record relations, historical upgrade tooling, or keeping `good_job` configuration names. Each such adaptation needs explicit documentation. A feature must stay planned until its DecentJob API, SQL behavior, failure cases, and meaningful specs exist.

DecentJob batches require all jobs and callbacks to share a DecentJob database object. Reopening starts a new callback generation; callback delivery history remains retained. Completion requests commit atomically with job state, and idle polling recovers pending delivery. Batch operations flush independently of an enclosing bulk capture. These implementation choices are documented in the README and do not imply exactly-once job execution or GoodJob table compatibility.

The largest implementation risks are:

1. PostgreSQL session ownership, fork safety, crash recovery, and mixed lock strategies. The reference's concurrent-worker tests establish no duplicate execution under those test conditions. They do not establish exactly-once external side effects after a process crash.
2. Concurrency claims and promotion races. A counter plus delayed retries does not reproduce durable claims, pending promotion, fair waiting order, and multi-rule cleanup.
3. The dependency limit. Cron parsing, worker scheduling, HTTP/dashboard rendering, CLI parsing, and process supervision need owned implementations or optional host adapters. A small cron parser must not be labeled equivalent to the reference's accepted Fugit schedules without conformance evidence.
4. Transaction boundaries. A private `pg` connection cannot automatically join an application's Active Record transaction. The API must define caller-owned connection use or host after-commit integration, and test rollback visibility.
5. Scope hidden in the dashboard. Performance ranges, DST editing, bulk filtered actions, live refresh, and concurrency-claim rendering are separately observable features, not consequences of having a jobs table.
6. Source/spec inconsistencies. Examples sometimes have stale descriptions, and the top-level pause signature differs from the settings store. Read assertions and source together before translating a contract; record any chosen correction.
