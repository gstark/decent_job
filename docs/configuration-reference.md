# Configuration and global-control reference map

Compared on October 9, 2026 against GoodJob commit `ad4be5c2e10316354cb3d3d65a480b5450c7fd77`. The audit started from DecentJob `d65bd51` and incorporates the subsequent heartbeat/cron defaults and global-control checkpoints. Spec references identify source coverage; fresh run results are recorded in the [implementation plan](implementation-plan.md). Line numbers may move as implementation continues.

Scope: every public setting/helper in reference `lib/good_job/configuration.rb`, the command/options in `lib/good_job/cli.rb`, and the public controls in `lib/good_job.rb`, including its ThreadStatus and LifecycleHooks extensions. Dashboard configuration remains deferred. This report does not claim all other parity rows are complete.

## Global-control capabilities and adaptations

The three gaps found by the configuration audit now have library APIs:

1. `DecentJob.shutdown?` observes the registered workers and cron managers owned by global shutdown. It is true before startup and after all owned resources drain. It does not signal shutdown or change lifecycle state. Directly owned resources remain the caller's responsibility. Reference `lib/good_job.rb:189` aggregates capsules; DecentJob aggregates its resource registry. See `spec/global_controls_spec.rb`, `spec/global_shutdown_drain_spec.rb`, and [lifecycle inspection](lifecycle.md#shutdown-completion).

2. `DecentJob.migrated?(database: nil)` and `Schema#migrated?` check every packaged migration version through the connection's search path. Missing metadata or versions return false, extra future versions are allowed, and database errors other than missing metadata propagate. A savepoint preserves the caller's transaction on query errors. The check never installs tables. Reference `lib/good_job.rb:330` checks one concurrency-claim table; DecentJob deliberately checks its full version history. See `spec/schema_readiness_spec.rb`, `spec/schema_spec.rb`, and the packaged-gem verification in the implementation plan.

3. `DecentJob.perform_inline(queues: "*", limit: nil)` drains until no eligible job remains, including immediate retries, and returns the number of attempts. A nonnegative integer caps attempts; zero returns without opening the database. Future jobs remain pending until due and unhandled errors propagate. This matches the reference's unbounded default at `lib/good_job.rb:294`, with keyword queue selection and stricter limit validation. PostgreSQL remains the due-time authority, so Ruby-only test time travel deliberately does not match the reference. See `spec/global_controls_spec.rb`.

Intentional configuration differences remain. Configuration `shutdown_timeout` defaults to 30 finite seconds rather than the reference's -1 indefinite wait; method-level nil/zero/force behavior is documented separately. Blank queue expressions and empty pipe or semicolon groups, including trailing separators, are rejected. Nonpositive cron graceful restart periods are invalid rather than mapped to nil. CLI application loading requires explicit `--require`. Pool sizing counts DecentJob connections rather than estimating all Ruby threads or warning about a shared Active Record pool. Explicit false wins over lower configuration sources.

Development heartbeat defaults, blank cron-source fallback, and effective cron enablement are covered by `spec/configuration_defaults_spec.rb` and real Rails cases. The configuration mapping is complete for the library; dashboard settings remain deferred. The final [library parity audit](library-parity-audit.md) records the broader review; benchmarks remain separate work.

## Source rules applying to all rows

Reference normally combines explicit `options`, live `Rails.application.config.good_job`, then ENV, but individual methods differ. Several booleans use nil-aware selection; `enable_cron` uses `||`, so explicit false can lose to Rails/ENV. Several cleanup methods ignore explicit options entirely. Reference `cron` reads global ENV directly, bypassing the constructor's injected env hash. Reference exposes mutable `options` and `env` readers and accepts `Configuration.new(options, env:)`.

DecentJob uses typed setters and a no-argument constructor, Rails `config.decent_job`, and captured ENV. Generic/specialized ownership gives explicit Ruby/CLI > current Rails options > construction ENV/default. Its lack of `options`/`env` accessors or an injected-env constructor is an API adaptation, not lost setting capability. Runtime environment replacement is deliberately not live. Removed host keys restore the captured baseline; nil semantics remain setter-specific. Copies recursively own Hash/Array/String containers and preserve application class/logger/callable identity. Candidate validation protects active configuration from failed `configure`, CLI, or Rails changes.

Proof: `spec/configuration_sources_spec.rb:59,72,84,123,132,140,154,170,201,217,231,250,275,306,322,338`; `spec/host_configuration_spec.rb:23,32,43,50`; docs `configuration.md:14-46`, `rails-integration.md:16`. ENV booleans use ActiveModel-compatible false strings, with blank normalized to false rather than nil; seven variables are exhaustively exercised at `configuration_sources_spec.rb:351`. Rails/Ruby setters retain individual validation and do not promise string-boolean coercion everywhere.

In the setting table, ENV names show suffixes. Reference uses `GOOD_JOB_`, DecentJob uses `DECENT_JOB_`, unless explicitly noted. Every ordinary DecentJob setting supports explicit Ruby and Rails sources. A dash in CLI means no reference flag and no need for one to preserve the feature. All flags shown are DecentJob spellings.

## CLI mapping

Reference start flags all have equivalents: queues, max_threads, subprocesses, poll_interval, max_cache, shutdown_timeout, idle_timeout, enable_cron, daemonize, pidfile, probe_port, probe_handler, queue_select_limit. Thor underscore names become OptionParser hyphen names. Explicit negative booleans are supported. Reference default command `start` and `cleanup_preserved_jobs --before-seconds-ago` map directly; ours adds alias `cleanup`, batch size and discarded selection, `migrate`, help/version, explicit require loading, dequeue/lock/priority/cron-grace/listen flags.

Reference CLI loads `config/environment.rb` automatically (`good_job/cli.rb:194`). Ours loads each `--require` file before applying CLI options (`decent_job/cli.rb:51-58`), permitting Rails or standalone applications. `rails-integration.md:14` documents the required Rails command. When migrating a Rails deployment, add `--require ./config/environment.rb` to the worker command. Standalone applications can require their own setup file. CLI flags are applied after required application setup and take precedence over application settings. Environment values remain the captured construction baseline. Registered adapters remain usable.

Reference `CLI.within_exe?`, `CLI.log_to_stdout?` and explicit stdout override map directly. `exe/decent_job:6` marks executable context before requiring application files. `logging_cli_spec.rb:30,42,54,61,94,104` proves default/override/idempotence/boot timing. Top-level `GoodJob.cli?` is equivalent to `DecentJob::CLI.within_exe?`; no extra capability is missing. Programmatic CLI run suppresses embedded worker startup through `with_cli_application` independently of executable identity.

Signal shutdown, daemon cleanup, idle exit, no-fork flattening, cluster hooks, probes and systemd are already mapped by S1-S8. Their direct configuration coverage is listed above; CLI/runtime coverage includes `cli_spec.rb:139,154,166`, `daemon_cli_spec.rb`, `health_services_cli_spec.rb`, `supervisor_configuration_spec.rb:57,70,90`, supervisor process specs. Fresh suite results are recorded with each implementation checkpoint. Reference process environment beyond Configuration, such as `NOTIFY_SOCKET` and watchdog variables, is covered by `health_services_spec.rb:126-390` and `health-services.md:54+`.
